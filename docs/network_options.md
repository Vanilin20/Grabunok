# Мережа для «Банди» в Unity: два варіанти

Тут лише порівняння, коду немає. Рішення за Іваном.

Спільне для обох варіантів:
- **Архітектура не змінюється (ТЗ).** Хост авторитетний: на ньому крутиться `HeistSim`, клієнти надсилають тільки дії й отримують знімок своєї ролі.
- **ITransport.** Екрани говорять із симуляцією через `ITransport`. Зараз це `LocalTransport` (усе на одному пристрої). Мережа стане ще однією реалізацією `ITransport`, і код екранів та `HeistSim` при цьому не міняється.
- **Транспорт.** В обох варіантах — Netcode for GameObjects (NGO) + Unity Transport (UTP). Від NGO беремо лише RPC і події підключення: стан справи йде не через NetworkVariable, а як знімок ролі через адресні RPC (`RpcTarget.Single`). Так «кожна роль бачить тільки своє» гарантує сама симуляція, а не налаштування видимості.

---

## а) Локальна Wi-Fi: NGO + власний пошук кімнати

Так само, як було в Godot: один телефон — хост (порт 7777), інші знаходять кімнату за 4-значним кодом через UDP-маяк у локальній мережі (порт 7778).

**Що налаштувати**
- Пакети `com.unity.netcode.gameobjects` і `com.unity.transport` через Package Manager. Без акаунта, без хмари, без Dashboard.
- Пошук кімнати пишемо самі за зразком Godot `network.gd`: хост раз на секунду шле broadcast-маяк `BANDA1|код|ім'я хоста|гравців|відкрита` на 255.255.255.255 та на broadcast-адреси підмереж. Клієнт слухає 7778, і кімната зникає зі списку, якщо маяка немає 3,5 с. Це `System.Net.Sockets.UdpClient`, працює на Android.
- Android: дозвіл `INTERNET` (Unity додає сам). Для отримання broadcast на деяких телефонах потрібен `WifiManager.MulticastLock` — це рядок Java-коду через `AndroidJavaObject`.
- Запасний шлях, як у Godot: ручне введення IP хоста.

**Безкоштовні ліміти:** сервісів немає, тож і лімітів немає. Трафік іде всередині Wi-Fi.

**Затримка:** 1–10 мс у домашній Wi-Fi. Пакети не виходять з роутера.

**Складність:** середня. Більше коду, ніж у варіанті б), бо пошук і перепідключення пишемо самі. Зате кожен рядок прозорий, і все вже один раз зроблено в Godot (~365 рядків `network.gd`).
- Ризик з ТЗ: публічні та гостьові Wi-Fi часто блокують трафік між пристроями (client isolation). Обхід — точка доступу з телефона хоста.
- Гра тільки в одній кімнаті (одна мережа).

**Як відтворити мережеві тести Godot (`tests/net_bot.gd`)**
- Один ПК, три процеси Unity-збірки в batch-режимі: `Banda.exe -batchmode -nographics -bot host|shadow|safe`. Кожен бот друкує `PASS/FAIL` і завершується з кодом 0/1.
- Скрипт `tools/net_test.sh` запускає всі три й збирає результат.
- Перевірки дослівно з Godot:
  1. Пошук кімнати за кодом (з фолбеком на 127.0.0.1, бо на одному ПК broadcast може не ходити).
  2. Хакер має схему й не має комбінації; не отримує позицію Тіні.
  3. Тінь не отримує ні схему, ні комбінацію; отримує свою позицію, але не стан камер; Тінь рухається.
  4. Зломщик має комбінацію й не має схеми; хибна комбінація → помилка.
  5. Обрив посеред справи → перепідключення на ту саму роль зі збереженим станом сейфа (токен гравця, як у Godot); правильна комбінація відкриває сейф.
  6. Камера вимикається після дії Хакера; помилка на сейфі піднімає тривогу; у спільному стані 3 гравці.
- Додатково можна запускати Multiplayer Play Mode (`com.unity.multiplayer.playmode`, до 4 гравців в одному редакторі) для ручної перевірки. Головний тест — збірки в batch-режимі, бо вони ближчі до телефонів.

## б) Онлайн: Unity Relay + Lobby

Хост створює Lobby з кодом кімнати й Relay-алокацію, а клієнти з будь-якої мережі (Wi-Fi, мобільний інтернет) заходять за кодом. Увесь трафік іде через сервери Relay, власного сервера не треба. Хост, як і раніше, телефон гравця.

**Що налаштувати**
- Акаунт Unity, проєкт у Unity Cloud Dashboard (прив'язка Project ID у Edit → Project Settings → Services). Увімкнути Relay і Lobby.
- Пакети: NGO, UTP і Multiplayer Services SDK (`com.unity.services.multiplayer`: сесії з Lobby + Relay в одному API) або окремі `com.unity.services.relay` / `com.unity.services.lobby`.
- Анонімна автентифікація (`AuthenticationService.SignInAnonymouslyAsync`): кожен телефон отримує Player ID без реєстрації.
- Хост: `CreateSessionAsync` (створює Lobby + Relay-алокацію), код кімнати = join code сесії. Клієнт: `JoinSessionByCodeAsync`.
- Lobby потребує heartbeat від хоста, інакше кімната зникає. SDK сесій робить це сам.

**Безкоштовні ліміти** (офіційна сторінка цін: <https://unity.com/products/gaming-services/pricing>, перевірено 12.11.2026)
- Relay — CCU: перші 50 середньомісячних CCU безкоштовно (≈ 2 160 000 хвилин з'єднання). Далі $0.16 за кожен додатковий середній CCU.
- Relay — трафік: 3 GiB на CCU безкоштовно, максимум 150 GiB/місяць (US/EU/Азія-Австралія разом). Далі $0.09/GiB (US+EU), $0.16/GiB (Азія+Австралія). При меншому CCU безкоштовний трафік теж менший: <https://support.unity.com/hc/en-us/articles/4410136449812-How-is-the-Relay-Service-Priced>.
- Lobby — трафік: 10 GiB/місяць безкоштовно на регіональну групу (US+EU та Азія+Австралія). Далі $0.09 / $0.16 за GiB.
- Ліміти запитів (<https://docs.unity.com/ugs/en-us/manual/lobby/manual/rate-limits>): гравцю — створення сесії 20/хв, вхід 1/с, оновлення 60/хв, перепідключення 1/с. Relay: створення алокації, join code і вхід — по 60/хв на гравця.
- Важливо: якщо перевищити безкоштовний ліміт без платіжних даних, доступ до сервісів UGS блокується (<https://docs.unity.com/en-us/services/pricing-and-billing>).
- Оцінка для «Банди»: партія — 3–5 телефонів, ~10 хв. 50 середніх CCU — це ~50 людей, які грають цілодобово весь місяць. Для плейтестів і перших сотень гравців — з величезним запасом.
- Трафік: знімок ролі ~0,5–1 КБ × 15/с × 4 клієнти ≈ 30–60 КБ/с на партію ≈ 20–35 МБ за 10 хв. 150 GiB — це тисячі партій на місяць.

**Затримка:** плюс один хоп до найближчого регіону Relay (для України — Європа). Типово +20–60 мс до кожного пакета, мобільний інтернет — 50–150 мс. Для «Банди» (оновлення 10–20/с, покрокові міні-ігри, рух Тіні зі згладжуванням) це некритично. Точних гарантій Unity не публікує — це моя оцінка, перевіряти на телефонах.

**Складність:** найменше власного коду: пошук і NAT уже розв'язані сервісом, `JoinByCode` — один виклик.
- Проблеми: потрібен інтернет навіть за одним столом; залежність від хмари й акаунта; обробка помилок сервісу (тайм-аути, ліміти запитів, вихід хоста = кінець сесії); асинхронна автентифікація перед лобі.
- Міграції хоста в Relay немає: телефон хоста вимкнувся — справа закінчилась (як і у варіанті а).

**Як відтворити мережеві тести Godot**
- Ті самі три боти з тими самими перевірками, що й у варіанті а), тільки бот-хост створює сесію в Relay, а боти-клієнти заходять за кодом. Це тест через реальний інтернет.
- Кожен бот — окремий профіль автентифікації (`AuthenticationService.SwitchProfile`), бо на одному ПК інакше всі матимуть однаковий Player ID.
- Перепідключення посеред справи: клієнт рве з'єднання (`NetworkManager.Shutdown`) і заходить знову тим самим кодом; хост за токеном повертає йому ту саму роль і стан.
- Мінус: тести залежать від мережі й лімітів запитів (вхід 1/с), тож у CI вони повільніші й «мерехтять». Для щоденних прогонів варто лишити локальний `UnityTransport` на 127.0.0.1 як режим тестів, а з Relay ганяти рідше.

## Порівняння

| | а) Локальна Wi-Fi | б) Relay + Lobby |
|---|---|---|
| Де грати | одна Wi-Fi (або точка доступу хоста) | будь-де з інтернетом |
| Акаунти / хмара | не треба | акаунт Unity, проєкт у Dashboard |
| Безкоштовно | без лімітів | 50 CCU, 150 GiB Relay, 10 GiB Lobby / міс |
| Затримка | 1–10 мс | +20–60 мс (мобільний інтернет до 150 мс) |
| Власний код | пошук, маяк, перепідключення | майже нічого, але обробка помилок сервісу |
| Ризики | client isolation у публічних Wi-Fi, broadcast на Android | потрібен інтернет, ліміти запитів, залежність від сервісу |
| Тести | 3 процеси на 127.0.0.1, швидко й стабільно | через інтернет, повільніше; локальний режим для CI |
| Відповідність ТЗ | етап MVP («локальна Wi-Fi») | етап 5 («онлайн») |

## Моя рекомендація

**Зробити а) зараз, але на транспорті, який дозволяє додати б) без переписування.** Аргументи:
1. **ТЗ.** MVP — «троє друзів за одним столом». Локальна Wi-Fi закриває це повністю, без акаунтів, лімітів і інтернету. Онлайн у ТЗ — етап 5.
2. **Тести.** Мережеві тести Godot (хост + 2 клієнти, ролі, перепідключення) найлегше й найстабільніше відтворити на 127.0.0.1. Вони мають бути зеленими в кожному прогоні, а не залежати від хмари.
3. **Перехід потім дешевий.** NGO + UTP однакові в обох варіантах. Relay — це інші параметри `UnityTransport` (`SetRelayServerData`) і інший спосіб отримати код кімнати. З `ITransport` додати б) пізніше — це одна нова реалізація «знайти/створити кімнату», а `HeistSim`, екрани й тести не міняються.
4. **Ризик Wi-Fi закриваємо так само, як у Godot:** точка доступу з телефона хоста + ручний IP.

Коли варто брати б) одразу: якщо плейтести будуть дистанційні (друзі в різних містах). Тоді локальна мережа не допоможе, і варто відразу робити Relay + Lobby, залишивши 127.0.0.1-режим для тестів. Це відкрите питання з ТЗ: «чи можна грати онлайн з різних міст».

# Банда — мобільна кооп-гра про пограбування

## Контекст
- Гра описана в `docs/TZ.md`. ТЗ — головне джерело правди. Якщо пропонуєш щось, що з ним розходиться, прямо скажи про це і поясни чому.
- Рушій: Unity 6.3 LTS (6000.3), мова C#. URP 2D (Renderer2D, Light2D), інтерфейс uGUI + TextMeshPro, ввід — Input System.
- Керування редактором — Unity MCP (сцени, компоненти, Play, консоль, знімки). Godot-версія (гілка main) — джерело логіки й арту для перенесення.
- Платформа: телефони, спершу Android. Розробка на Windows (Lenovo Legion 5).
- Репозиторій: github.com/Vanilin20/Grabunok, Unity-версія — гілка unity-migration
- Поточний етап: 1 — технічний прототип (див. `docs/TZ.md`, розділ «MVP і план розробки»).

## Розподіл роботи
- Claude пише код, сцени (.unity — збираються кодом, див. «Сцени»), ресурси й налаштування проєкту.
- Claude робить увесь візуал: спрайти, анімації, тайли, UI, освітлення, частинки, шейдери. Готові ассет-паки й AI-генерація — лише як доповнення, якщо так помітно краще.
- Іван запускає, тестує на телефонах і збирає APK. Арт не малює: дає мудборди, начерки й референси.
- Якщо щось треба зробити руками в редакторі Unity, дай покрокову інструкцію: куди натиснути, який обʼєкт чи компонент створити, що куди перетягнути.

## Планка якості
- Ціль — рівень випущених піксель-арт інді-ігор з сильним світлом і атмосферою (орієнтири за рівнем: Monaco, Katana Zero, Hyper Light Drifter, Kingdom). Перед кожною візуальною задачею порівнюй свій рендер з цим рівнем чесно, а не з «для прототипу нормально».
- «Заглушка» дозволена ТІЛЬКИ для логіки, якої ще немає. Будь-який екран, який бачить гравець, має відповідати стандартам арту нижче. Простий вигляд з підписом «заглушка» — заборонено.
- Не занижуй результат наперед. Спершу найкращий варіант, потім чесна оцінка. Відмова — тільки через реальне технічне обмеження, назване конкретно.
- Задача з візуалом не вважається виконаною, поки Іван не побачив скріншоти.

## Стандарти арту
- Жодних векторних примітивів (кола, прямокутники з draw_*, ColorRect як обʼєкт сцени) для ігрових обʼєктів, персонажів, меблів, стін чи інтерфейсу ролей. Тільки піксель-арт спрайти й тайли. Примітиви допустимі лише як технічні маски чи службові оверлеї.
- Атмосферне 2D: нічне місто, дощ, неон, ліхтарі, глибокі тіні. Одна палітра (16–32 кольори, файл палітри в репо), світло з одного напрямку, розмір тайла 16×16, базова роздільність 640×360, фільтр Nearest.
- Кожен ігровий екран має щонайменше 3 шари глибини (фон, ігровий план, передній план) і власне освітлення: PointLight2D, тіні від LightOccluder2D, CanvasModulate для ночі.
- Кожен екран має живі деталі: частинки (дощ, пил, пара, іскри), анімоване світло (мерехтіння неону, ліхтарик), рух у фоні. Статичний кадр без руху — брак.
- Обʼєкти мають обʼєм: щонайменше 3–4 тони на матеріал, контур або виразний силует, текстура (цегла, плитка, метал, дерево). Плаский заливний колір на великій площі — брак.
- Персонажі: силует читається в масштабі 1x, ходьба мінімум 6 кадрів, idle-анімація з диханням, вторинний рух. Жодних «сирітських» пікселів і подушкового шейдингу.
- UI ролей — діегетичний, ніби пристрій у руках: у Хакера екран ноутбука з CRT-ефектом і сканлайнами, у Зломщика масивний сейф з металом, заклепками й тінню на весь екран, у Тіні вид з ліхтариком і відчутний простір навколо. Мінімум тексту, усе читається за пів секунди.
- Активні кнопки чітко світяться, неактивні явно відрізняються. Контраст тексту — не нижче 4.5:1.

## Композиція, світло, персонажі
- У кожного кадру один фокус. Найважливіше (персонажі, головна дія) — найконтрастніше й найкраще освітлене місце.
- UI стоїть на спокійній ділянці кадру (небо, темний план, віньєтка) або на власній підкладці й не перекриває найдеталізованіші частини фону.
- Кожне джерело світла логічне: неон, ліхтар, вікно, екран підсвічують поверхні навколо себе своїм кольором зі спадом яскравості. Відображення й відблиски фізично можливі: тільки під джерелом, з урахуванням відстані й кута.
- Світло робить роботу, а не намальоване пласко: PointLight2D з текстурами, normal maps для цегли, металу й персонажів там, де це дає обʼєм, WorldEnvironment glow для неону.
- Атмосферна перспектива: що далі шар, то менше контрасту й більше туману чи кольору неба.
- Персонажі мають rim light від найближчого джерела й відділяються від фону силуетом і контрастом. Силует читається навіть залитий одним кольором.
- Повторювані елементи (вікна, цегла, плитка) мають варіації: різне світло, силуети в кімнатах, штори, кондиціонери, поламана плитка, сміття. Ідеальна сітка — брак.
- Кожен стан UI пояснює себе: вимкнена кнопка показує, чого бракує. Кнопки мають hover, pressed, disabled і звук натискання.
- Обличчя персонажів не можуть бути пласкими плямами: навіть у 16 px — тінь, блиск очей чи силует маски/капюшона.
- Тіла не можуть бути суцільними темними масами: складки, руки, ремені, підсвічені краї.
- Найяскравіший обʼєкт кадру — або фокус, або змістовний. Велика яскрава пляма без змісту — брак.
- Кути кадру не можуть бути мертвими: або життя, або свідома віньєтка.
- Еталон якості — головне меню (docs/art/menu-backlog.md — його відкладені правки). Кожен ігровий екран — на його рівні або вище.
- Продуктивність — частина якості: 60 FPS на середньому Android (рендерер Mobile). Якщо ефект не тягне — оптимізуй, а не прибирай.

## Перевірка якості
- Автоматичні перевірки з tools/checks/ запускаються перед кожним показом Івану.
- Незалежний субагент-рецензент оцінює кожен екран. Поріг — 8 з 10 по кожному критерію. Пороги якості не знижуються ніколи.
- Звук Claude не чує: звуки підбираються з поясненням вибору, оцінює Іван.
- Те, що можна перевірити тільки на телефоні, завжди йде окремим списком «не перевірено».

## Цикл якості для візуалу
1. Перед роботою перечитай стайлгайд і референси з docs/art/.
2. Зроби, відрендери кожен змінений екран у PNG (рендер камери в RenderTexture через BandaCapture — див. «Як рендерити скріни») і переглянь.
3. Пройди чекліст «Стандарти арту» пункт за пунктом і для кожного напиши: так/ні. Будь-яке «ні» — переробляєш.
4. Назви 3 найслабші місця, порівнявши з рівнем орієнтирів, і виправ їх. Мінімум 3 ітерації.
5. Показуй Івану фінал: скріншоти до/після, заповнений чекліст і список покращень.

## Правила відповідей
- Відповідай українською, коротко і структуровано.
- Спершу діагноз проблеми, потім виправлення. Не латай симптоми.
- Тільки C# для Unity 6.3: явні типи, [SerializeField] private замість public-полів, корутини/async замість блокувань. Не вигадуй API: якщо не впевнений, що метод існує в Unity 6.3 чи пакеті потрібної версії, перевір у Library/PackageCache, через Unity MCP або запуском.
- Одна задача — один логічний крок. Великі задачі ділимо на частини.
- В кінці: що Івану перевірити і що саме має статися.
- Окремо позначай, що можна перевірити тільки на реальному телефоні (вібрація, гіроскоп, мікрофон, мережа між пристроями).
- Перед великими змінами архітектури спершу запитай.

## Стандарти коду
- Назви змінних, функцій і файлів англійською (snake_case для файлів), коментарі українською.
- Типізація всюди, де можливо.
- Зв'язок між обʼєктами через C#-події (event Action) і посилання, задані в інспекторі, а не пошук далеких обʼєктів (GameObject.Find) під час гри.
- Глобальний стан — тільки в системних синглтонах на обʼєкті Systems (GameState, транспорт тощо). Логіка справи — чистий C# без MonoBehaviour (HeistSim), щоб її можна було тестувати й запускати на хості.
- Логіка гри живе на хості. Клієнти лише надсилають дії й показують те, що отримали; кожна роль отримує тільки свої дані.
- Жодних прихованих TODO: незроблене позначай явно.
- Мережевий код обробляє обрив з'єднання й пізнє підключення.

## Перевірка перед комітом
Перед кожним комітом проєкт має компілюватися й запускатися без помилок:

```bash
bash tools/check_compile.sh          # остання компіляція в Editor.log: 0 помилок, 0 попереджень C#
```

Плюс через Unity MCP (або вручну в редакторі):
1. Refresh + компіляція (`refresh_unity` з `compile: request`), потім `read_console` — без помилок.
2. EditMode-тести (Window → General → Test Runner або `run_tests`) — усі зелені.
3. Play головної сцени Assets/Scenes/Main.unity ~2 с — у консолі немає Error/Exception.

Без запущеного редактора (CI, нічна перевірка):
```bash
Unity.exe -batchmode -nographics -projectPath . -runTests -testPlatform EditMode -testResults Captures/tests.xml -quit
```

Для візуалу — рендер у PNG і перегляд (цикл якості вище).

## Як рендерити скріни
- Game view не оновлюється, коли вікно Unity без фокусу, тому скріншот вікна ненадійний.
- Використовуй `Banda.EditorTools.BandaCapture.Capture(path, width, height)` (через `execute_code` у Play): камера рендерить у RenderTexture, Canvas на час знімка переходить у Screen Space - Camera.
- Основний рендер — 1280×720 (2× від базових 640×360); «як на телефоні» — 640×360 і зменшений до 50%.
- Для порівнянь паралакс заморожується: `BackdropParallax.Frozen = true`.
- Знімки й звіти — у `Captures/`, порівняння з Godot — у `docs/art/compare/`.

## Сцени
- Сцени не правляться руками: їх збирає код (`Assets/Scripts/Editor/BandaSceneBuilder.cs`, меню **Banda → 2. Зібрати сцену Main**). Ручна правка зникне при наступній збірці.
- Налаштування імпорту арту (Point, без стиснення, 1 px = 1 одиниця, нормалі) — `BandaAssetSetup` (**Banda → 1. Налаштувати ассети**).
- Згенерований арт (текстури з коду) — генератори в `Assets/Scripts/Editor/Art/`, результат — PNG у `Assets/Art/`.

## Відповідність термінів Godot → Unity
Стандарти арту й світла вище написані мовою Godot і лишаються дослівно. У Unity вони означають:

| Godot | Unity (URP 2D) |
|---|---|
| PointLight2D | Light2D (Point), радіус = 64 × texture_scale |
| LightOccluder2D | ShadowCaster2D |
| CanvasModulate (ніч) | Global Light 2D (колір і інтенсивність ночі) |
| WorldEnvironment glow | Volume з Bloom |
| CPUParticles2D | ParticleSystem |
| draw_*, ColorRect як обʼєкт сцени | Image/SpriteRenderer з однотонним спрайтом — так само заборонено для ігрових обʼєктів |
| autoload | синглтон на обʼєкті Systems |
| сигнали | C#-події |
| 640×360, canvas_items, expand | ортокамера size 180, CanvasScaler 640×360 Expand |

## Структура проєкту
```
Assets/
  Scenes/          — Main.unity (згенерована)
  Scripts/
    Core/          — GameState, палітра, ролі
    Heist/         — HeistSim (чистий C#), ITransport, LocalTransport
    UI/            — екрани й компоненти інтерфейсу
    Roles/         — екрани ролей
    Backdrop/      — живий фон міста
    Editor/        — збирач сцени, налаштування ассетів, генератори арту, знімки
  Tests/EditMode/  — тести Unity Test Framework
  Art/             — спрайти, UI, шрифти, матеріали (Menu/, Fx/, UI/, Fonts/, Heist/)
  Audio/           — звуки
  Data/            — макети (menu_layout.json тощо)
docs/              — ТЗ, стайлгайд, порівняння з Godot, мережеві варіанти
tools/             — перевірки (check_compile.sh)
Captures/          — знімки й нічні звіти
```
